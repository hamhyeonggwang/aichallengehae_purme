# n8n 워크플로우 — 기관 내부 실행 경로

이 폴더는 **본선에서 실제 현장에 배치할 구조**입니다.
웹 프로토타입(`app/`)과 같은 로직을, 기관 내부망에서 개인정보를 밖으로 내보내지 않고 실행합니다.

> ⚠️ 이 워크플로우는 아직 **import 검증을 거치지 않은 초안**입니다.
> n8n 버전에 따라 노드 typeVersion 조정이 필요할 수 있습니다.

---

## 왜 두 벌인가

| | 웹 프로토타입 | n8n 워크플로우 |
|---|---|---|
| 목적 | 심사위원이 흐름을 이해·체험 | 현장에서 실제 실행 |
| 실행 위치 | Vercel (공개 웹) | 기관 내부망 |
| 추출 모델 | Gemini API (서버 프록시) | **Ollama 로컬** |
| 데이터 | 가상 데이터 고정 | 기관 CSV |
| 트리거 | 사람이 붙여넣기 | 문자 수신 웹훅 |

**매칭 규칙은 두 곳이 동일합니다.** `lib/matcher.ts`와 `매칭 규칙 엔진` 노드는 같은 조건·같은 정렬을 씁니다. 웹에서 확인한 결과가 현장에서도 같게 나옵니다.

## 왜 첫 노드가 "입력 정규화"인가

당일 결석의 접수 지점은 고정되어 있지 않습니다. 코디네이터로 들어오기도 하고, 담당 치료사에게 직접 전달되기도 합니다. 유입 경로에 따라 다른 한쪽이 인지하지 못합니다.

이후 처리 경로도 분산되어 있습니다.

| 단계 | 채널 |
|---|---|
| 결석 접수 | 문자 · 코디 입력 · 치료사 전달 |
| 치료사 공지 | 메신저 |
| 가능 여부 회신 | 메신저 · 구두 |
| 배정 확정 | 별도 시스템 |
| 보호자 안내 | 문자 |

**결과: 현재 몇 건이 비어 있는지 파악하는 단일 주체가 없습니다.** 그래서 몇 건이 회수되고 몇 건이 사라졌는지도 집계되지 않습니다.

`입력 정규화` 노드는 어느 주체가 어느 채널로 넣든 동일 형태로 변환해 하나의 흐름에 태웁니다. 이 워크플로우를 통과한 건은 전부 기록이 남습니다 — 후보를 찾지 못한 건까지 `후보 없음 기록` 노드에 남습니다.

**배정보다 계측이 먼저입니다.** 손실 규모를 모르는 상태를 먼저 종료해야 합니다.

접수 경로를 추가하려면 `결석 문자 수신` 앞에 트리거 노드(Gmail, Slack, 카카오, 내부 폼 등)를 붙이고 `입력 정규화`가 읽는 필드명만 추가하면 됩니다.

## 설치

### 1. n8n 자체 호스팅

```bash
docker run -d --name n8n \
  -p 5678:5678 \
  -e GENERIC_TIMEZONE=Asia/Seoul \
  -e TZ=Asia/Seoul \
  -v n8n_data:/home/node/.n8n \
  -v /path/to/data:/data \
  docker.n8n.io/n8nio/n8n
```

`/data`에 대기 명단 CSV를 두면 `대기 명단 읽기` 노드가 읽습니다.

### 2. Ollama

```bash
ollama pull qwen2.5:7b
ollama serve
```

n8n을 도커로 띄웠다면 `Ollama 추출` 노드의 URL을
`http://host.docker.internal:11434/api/generate`로 바꾸십시오.

### 3. 워크플로우 가져오기

n8n 화면 → Workflows → Import from File → `workflow.json`

### 4. 시험

```bash
curl -X POST http://localhost:5678/webhook-test/absence-intake \
  -H 'content-type: application/json' \
  -d '{"text":"오늘 수치료랑 감통만 빼주세요. 물리치료랑 작업치료는 그대로 받을게요"}'
```

## 다른 기관에서 쓰려면

바꿀 곳은 **세 군데뿐**입니다.

| 바꿀 것 | 위치 |
|---|---|
| 서비스 종목 목록 | `추출 결과 파싱` 노드의 `THERAPIES`, `Ollama 추출` 노드의 프롬프트 |
| 일정 구조 | `매칭 규칙 엔진` 노드의 `OUTPATIENT_SESSIONS` |
| 대기 명단 | `/data/waitlist.csv` — `waitlist.sample.csv` 형식 참조 |

우선순위 규칙(잔여 기회 적은 순 → 대기 긴 순)을 바꾸려면
`매칭 규칙 엔진` 노드의 `passed.sort(...)` 한 줄만 고치면 됩니다.
**형평 기준을 어떻게 정할지는 각 기관이 결정할 몫이며, 그 결정이 코드 한 줄로 드러나도록 설계했습니다.**

## 개인정보 처리

- 식별정보는 모델 호출 전에 토큰으로 치환됩니다 (익명화 전처리)
- 실명이 존재하는 구간은 접수 직후와 발송 직전뿐입니다
- 대기 명단 CSV는 기관 서버 파일시스템에만 존재합니다
- 외부 API 호출 노드가 없습니다
- 승인 큐로만 전달하며 자동 발송하지 않습니다

## 익명화 설계

### 왜 두 단계인가

모델에 원문을 그대로 보내면, 모델이 로컬이든 외부든 **개인정보 경계가 모델 선택에 종속**됩니다.
로컬 모델의 성능이 부족해 외부 모델로 바꾸는 순간 경계가 무너집니다.

익명화를 앞단에 두면 이 종속이 끊어집니다.

| | 익명화 없음 | 익명화 있음 |
|---|---|---|
| 로컬 모델 | 안전 | 안전 |
| 외부 모델 | **위험** | 안전 |
| 모델 교체 | 재심사 필요 | 영향 없음 |

**모델 성능과 개인정보 보호가 분리됩니다.** 정확도가 부족하면 모델을 바꾸면 되고,
경계는 익명화 노드가 계속 지킵니다.

### 처리 대상

| 종류 | 방식 | 신뢰도 |
|---|---|---|
| 대상자 성명 | 기관 명부 사전 대조 | 높음 |
| 휴대전화번호 | 정규식 | 높음 |
| 주민등록번호 | 정규식 | 높음 |
| 생년월일 | 정규식 | 중간 |
| 등록·차트번호 | 정규식 | 중간 |

매핑 테이블(`mapping`)은 **해당 실행 컨텍스트 안에만 존재**하며, 모델 호출 노드로 전달되지 않습니다.
`재식별 매칭` 노드가 발송 직전에만 참조합니다.

### 운영 시 강화 방향

프로토타입은 n8n Code 노드(Pyodide)에서 표준 라이브러리만 사용합니다.
운영 환경에서는 Execute Command 노드로 로컬 파이썬 스크립트를 호출해
비식별화 전용 라이브러리를 적용할 수 있습니다. 이 경우 처리는 여전히 기관 내부에서 완결됩니다.

> ⚠️ n8n의 Python Code 노드는 Pyodide 기반이며 버전에 따라 입출력 접근 문법이 다를 수 있습니다.
> `_input.all()` 및 항목 접근 방식은 import 후 확인이 필요합니다.
